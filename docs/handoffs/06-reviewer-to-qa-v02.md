# Handoff: Reviewer → QA (v0.2)

Ревью проведено по коду итерации v0.2 и по результатам живого прогона обогащения
на 100 учреждениях с известными сайтами.

## Findings

### Блокирующие (исправлены до передачи в QA)

| # | Проблема | Где | Исправление |
|---|----------|-----|-------------|
| R1 | Job падал с `IntegrityError` на unique-констрейнте персон: одна и та же персона со второй страницы того же сайта вставлялась повторно, потому что сессия создана с `autoflush=False` и `SELECT` не видел pending-объект | `services/enrich.py` | `db.flush()` после `db.add` в `upsert_person` |
| R2 | Директора страховых компаний с партнёрских страниц попадали в `chief_physician` (реальный случай: 3 «директора» с `rodnv.ru/strahovye`) | `person_extractor.py`, `page_finder.py` | `DIRECTOR_TRAPS` отклоняет «директор» в контексте страховых/фондов/филиалов; `SKIP_LINK` не ходит на `strahov`/`insur`/`partner` |
| R3 | Сайты с сертификатами Минцифры РФ выглядели мёртвыми: certifi их не знает, `httpx` бросал `ConnectError`, код классифицировал это как `timeout` | `base.py`, `page_finder.py`, `site_discovery.py` | `classify_network_error` + однократный fallback на `verify=False` **только** при ошибке сертификата |
| R4 | Мёртвый домен съедал ~40 с (таймаут 20 с × 2 ретрая), из-за чего прогон на 100 записях был неприемлемо долгим | `page_finder.py` | таймаут снижен до 12 с, ретрай убран в пользу TLS-fallback |
| R5 | Отзывы пациентов давали ложные персоны («Мою операцию проводил заведующий отделением …»), а текст отзыва попадал в `department` | `person_extractor.py` | расширен `NOISE`, `DEPARTMENT` останавливается на `!?:()` |
| R6 | «ГКБ им. С.П. Боткина» распознавалось как ФИО «Боткина С.П.» в роли `deputy` | `person_extractor.py` | `EPONYM`-guard перед паттерном «инициалы + фамилия» |
| R7 | При исключении внутри учреждения сессия оставалась в сломанном состоянии и следующий `commit` мог упасть | `services/enrich.py` | `db.rollback()` в обработчике перед логированием |
| R8 | Кнопка Excel в админке уводила со страницы через `window.location.href` и ломала скачивание blob | `static/admin.js` | навигация убрана, скачивание только через blob + `revokeObjectURL` |

## Compliance — проверено

| Требование | Статус |
|-----------|--------|
| robots.txt соблюдается | да, `robots_allows` до каждого запроса; 2 домена отдали `blocked` и не обходились |
| Rate limit | `rate_sleep` после каждого запроса, по умолчанию 1 rps |
| Ботовый User-Agent с контактом | да, `PerinatalContactsBot` со ссылкой на репозиторий |
| HTML 2GIS / Яндекс.Карт не парсится | да, только официальные API по ключу |
| Произвольный URL от клиента не обходится | да, URL берутся только из `institutions.website` или из ответа OSM/2GIS; клиентский `url` принимается лишь в `source=html`, где действует `host_allowed` |
| Обход не выходит за домен учреждения | да, `_same_host` + глубина ≤2, ≤12 страниц |
| Живая рассылка невозможна случайно | да, нужен `dry_run=false` **и** `ALLOW_LIVE_MAIL=1`, отправка не реализована |
| Персональные данные | только служебные ФИО и должности из открытых официальных источников, с `source_url` для проверки |

## Идемпотентность — проверено

- Повторный `enrich` того же учреждения не создаёт дублей: upsert по `(institution_id, full_name_norm, role)`.
- Запись с `verified_manually = true` не перезаписывается автообогащением (`upsert_person` выходит раньше).
- Понижение достоверности игнорируется: `medium` не затирает `high`.
- `_recently_failed` не даёт долбить домены, упавшие за 7 дней; обходится флагом `force`.
- Удаление или правка персоны пересчитывает `chief_physician` / `pathology_head` через `_sync_institution_fields`.

## Обратная совместимость API

Ломающих изменений нет. `/institutions` получил только новый необязательный параметр
`has_chief`; поля `chief_physician` и `pathology_head` существовали с v0.1 и теперь просто
заполняются. Новые эндпоинты добавлены, старые не менялись. WP-плагин 0.2.0 работает и с
API v0.1, потому что читает поля через `!empty()`.

## Безопасность

- XSS в админке: весь вывод в HTML проходит через `esc()`, включая `source_url` в `href`.
- Admin-эндпоинты закрыты `require_admin_api_key` на уровне роутера, публичный
  `/institutions/{id}/persons` по умолчанию скрывает `low`.
- SSRF: обход не принимает URL от пользователя, только из БД и ответов API.

## Что должен проверить QA

1. Точность `chief_physician` на выборке ≥30 записей вручную — цель precision ≥90%.
2. Метрики после полного прогона против целей: chief ≥60%, pathology ≥25%, email ≥60%.
3. Повторный прогон `enrich` на тех же учреждениях — числа персон не должны расти.
4. Регресс: список, фильтры, поиск, Excel (оба листа), dry-run рассылка, WP-шорткод.
5. Зафиксировать в отчёте реальную достижимость целей: доля доступных доменов оказалась
   существенно ниже ожидаемой (см. ниже) — цели по chief/email, вероятно, недостижимы в этой
   итерации, и это нужно честно отразить, а не подгонять.

## Главное для отчёта QA

На прогоне 100 учреждений с уже известными сайтами доступными оказались лишь около трети
доменов: остальные дали `dns_error`, `refused`, `http_4xx/5xx` или таймаут. То есть основное
ограничение итерации — не качество извлечения, а **устаревшие адреса сайтов в данных v0.1**.
